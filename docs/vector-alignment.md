When we added element-wise array operators (`a + b` on `[N]T`), the strategy was to reinterpret the array's `[N x T]` storage as an LLVM vector `<N x T>` via a typed load, run a vector op like `fadd <4 x float>`, and store the result back. The IR generated by the first version looked correct, the compilation succeeded, and the produced binary segfaulted on the very first vector load. The cause was alignment, and the lesson is worth writing down because it will bite us again.

Every load and store instruction in LLVM IR carries an `align N` attribute that promises *to the backend* that the pointer is N-byte aligned. The backend is free to lower the instruction to whichever machine instruction it considers cheapest under that promise. On x86 with SSE/AVX, a `<4 x float>` load with `align 16` becomes `movaps` (move aligned packed single); the same load with `align 1` becomes `movups` (unaligned). `movaps` against a non-16-aligned address raises `#GP` and the OS turns that into `SIGSEGV`. The promise is therefore not optional: lying about alignment is undefined behaviour, and on x86 the failure mode is loud and immediate.

The LLVM-C call we use, `BuildLoad2(builder, type, ptr, name)`, does not accept an alignment argument. When you omit it, LLVM stamps the *ABI alignment of the loaded type* onto the instruction. For scalars this is fine (an `i32` load gets `align 4`, an `i64` gets `align 8`, both matching the natural alignment of any reasonable alloca). For vectors it is a trap. The ABI alignment of `<4 x float>` is 16, of `<4 x i32>` is 16, of `<8 x float>` is 32, and so on — vectors are aligned to their full size. But the array storage we are loading *from* is `[4 x float]`, whose ABI alignment is just the element alignment, 4. So you get IR that looks like:

```llvm
%6     = alloca [4 x i32], align 4
%lvec  = load <4 x i32>, ptr %6, align 16
```

The alloca only guarantees 4-byte alignment, but the load promises 16. The backend trusts the promise, emits `movaps`, and the program segfaults the moment that address happens to be 4-aligned-but-not-16-aligned. It can run "by accident" if the linker or stack layout puts the alloca on a 16-byte boundary — which is part of why this kind of bug is so easy to miss in tiny test programs and so dangerous in real ones.

There are three principled fixes.

**Match the load to the storage.** The array is element-aligned, so the load should say so. Concretely, after each `BuildLoad2`/`BuildStore` we call `SetAlignment(inst, alignof(elem_type))` — for `i32` and `f32` that is 4, for `i64`/`f64` it is 8. The backend then emits `movups`, which on every CPU made since Nehalem (2008) runs at the same speed as `movaps` when the address happens to be aligned, and just works when it isn't. This is the cheapest correct fix and the only one that requires no changes outside `array_binary_emit_vector`.

**Match the storage to the load.** Bump the alloca's alignment up to the vector's natural alignment whenever an array might be used in a vector op. This keeps `movaps` and shaves a tiny amount off pre-Nehalem hardware, but it is invasive: every site that allocates an array storage slot — literals, locals, parameters spilled to the stack, fields in structs — has to learn about vector alignment. It also wastes stack space on padding, and the moment you support arbitrary-N arrays you start needing alignment up to AVX-512 widths (64 bytes) for anything you might lower into a `<16 x float>`.

**Use a scalar loop and let the loop vectorizer pick alignment.** For very large arrays this is what we will eventually want anyway, because a single `<1024 x float>` value is hostile to the register allocator. The loop vectorizer is good at choosing aligned vs unaligned moves based on the alloca's actual alignment. Not applicable to our current strategy of one-shot vector ops on small fixed-size arrays.

We picked the first option, with `SetAlignment(inst, 1)` rather than the precise element alignment. `align 1` is the conservative ceiling — it tells LLVM "make no assumption at all" — and the resulting `movups` is identical in cost on modern x86. The reason for `1` rather than the element alignment is just that it is one fewer thing to keep in sync: if we ever add `[N]u8` or pack arrays differently, `align 1` keeps working without revisiting the rule. The cost is negligible and the safety is total.

Two things to remember when extending this:

When you add a new array op (scalar broadcast, element-wise multiply, reductions), the same `align 1` discipline applies to whichever load/store touches the array storage as a vector. The splat construction for a scalar broadcast does not need it — `InsertElement` and `ShuffleVector` operate on SSA values, not memory — but the moment you `BuildLoad2`/`BuildStore` a vector against an `[N x T]*`, set the alignment.

If we ever decide to opt into aligned moves for performance, the right place to do it is at the alloca, not at the load. Promise alignment exactly once, where the memory is created, and every subsequent vector load against that pointer can safely inherit it. Promising alignment at the load is a lie waiting to happen, because the load has no way to know how the pointer was allocated.

The TL;DR for future incidents: if you see SIGSEGV from a vector load that "looks right" in IR, check the `align` on the instruction against the `align` on the alloca it points to. Those two numbers must be consistent, and LLVM-C's default for vector loads is almost always wrong.
